# Proxy Tunnel — как устроено

Для разработчиков. Инструкция для пользователей — [README.md](README.md).

Программа держит SSH-туннель к своему зарубежному серверу и пускает через него только выбранные домены
(по умолчанию Claude, Anthropic, Threads) и Claude Code целиком. Остальное идёт напрямую. Две версии с одним
устройством: macOS (`menubar/`, Swift) и Windows (`windows/`, C# / .NET 8); сервер у них общий — `server/`.

## Схема

```
компьютер                                          сервер (Ubuntu/Debian)
Claude Code ── HTTPS_PROXY ─┐
браузер, Claude.app ── PAC ─┤
                            └─ 127.0.0.1:8888 ══ ssh -L ══ tinyproxy 127.0.0.1:8888 ── интернет
```

- **Сервер универсальный**: только tinyproxy, слушающий `127.0.0.1`, и пользователь `tunnel`, которому
  разрешено одно — проброс на этот порт (`restrict,port-forwarding,permitopen=…` в `authorized_keys`,
  `ForceCommand nologin`). О Claude сервер ничего не знает.
- **Скрипты сервера** — `server/setup.sh` (tinyproxy и пользователь туннеля) и `server/no-password.sh` (вход
  только по ключу; при ошибке возвращает прежние настройки ssh). Обе версии вшивают их в себя. Повторный
  запуск безопасен; ошибка — строка `PT-ERROR: …` и код не 0; успех — последняя строка «сервер готов» /
  «вход по паролю выключен».
- **На компьютере** программа держит туннель (переподключение с паузой 3 → 60 с), раздаёт PAC-файл из памяти
  на `127.0.0.1:8889` и, когда туннель включён, ставит:
  - адрес PAC в системные настройки прокси (macOS — на все включённые сетевые службы, Windows — в настройки
    прокси пользователя);
  - `env.HTTPS_PROXY` = `http://127.0.0.1:8888` и `env.NO_PROXY` = `localhost,127.0.0.1,::1,.ru,.xn--p1ai,<сервер>`
    в `~/.claude/settings.json` (другие ключи не трогаются, перед записью — копия `.bak`).
- PAC и `HTTPS_PROXY` без запасного прямого пути: нет туннеля — эти домены не открываются вовсе, а не уходят
  с российского адреса. **Обратная сторона: туннель сломан — Claude Code не отвечает**, пока туннель не починят
  или не выключат (выключение и выход снимают прокси; после аварийного закрытия программа снимает их при
  следующем запуске, на Маке есть ещё `mode.sh off`). Уже открытые сессии Claude Code помнят прокси с момента
  старта — после включения или выключения туннеля их перезапускают.

## Поведение

- **При запуске туннель выключен**; настроенная программа сразу показывает панель, включают нажатием на
  верхнюю карточку (она же выключатель). Ненастроенная открывает окно настроек. После успешной настройки
  сервера туннель включается сам.
- **Проверки** (кнопка «Проверить», фоном каждые 2 минуты), по реальному пути, а не по настройкам:
  1. туннель подключён (на Маке — и через какой интерфейс идёт само ssh);
  2. выход через туннель — `claude.ai/cdn-cgi/trace` через прокси видит адрес сервера, не RU;
  3. Claude Code → туннель — прокси в `~/.claude/settings.json`;
  4. сайты из списка → туннель — PAC применяется системой (macOS — `scutil --proxy`, Windows — реестр) и
     раздаётся. Сообщение «Туннель включён для Claude» — только после того, как все четыре прошли.
- **Список сайтов** действует на браузер и приложения, берущие прокси из системы. Программы со своими сетевыми
  настройками (терминальные утилиты, Codex в VS Code) его не учитывают. Claude Code идёт через туннель целиком.

## Настройка сервера из программы

Вкладка «Автоматически»:

1. Пользователь вписывает адрес. Через секунду программа **в фоне** пробует войти админом (`root`) по ключу —
   ключ входа программы и ключи пользователя (`~/.ssh`; на Маке ещё агент). Тот же вход читает, включён ли вход
   по паролю (`sshd -T`), и заполняет блок «Доступ к серверу».
2. Только если ни один ключ не подошёл, появляются логин, пароль и галочка «Создать ключ для входа и добавить
   его на сервер» (включена). Пароль нигде не сохраняется.
3. «Настроить сервер»: ключ туннеля → вход → `setup.sh` → ключ входа админа (проверяется отдельным входом) →
   настройки сохраняются → туннель включается → выход через туннель. Для уже настроенного сервера кнопка
   называется «Настроить заново…» и спрашивает подтверждение.

Блок «Доступ к серверу»: «Вход по ключу» — «работает (проверено при настройке / при открытии настроек)» или,
после кнопки «Проверить соединение» (три входа подряд), «стабилен, 3 из 3». «Выключить вход по паролю» —
только когда вход по ключу подтверждён; после скрипта программа снова входит по ключу.

Вкладка «Вручную» — команда в буфер обмена для консоли хостинга (вход только через консоль, хостинг требует
сменить пароль при первом входе).

**Ограничение частоты подключений.** На серверах бывает `ufw limit` на ssh: 6 подключений за 30 секунд с одного
адреса, дальше «Connection refused». Поэтому команды настройки идут через одно подключение (Mac — общее
соединение `ControlPath=/tmp/pt-%C`, Windows — один `SshClient`), а «Проверить соединение» при отказе ждёт
30 секунд и повторяет, не считая это провалом ключа.

## Обновления и статистика

Раз в день (и ещё раз — при первом за день включении туннеля) программа делает один GET на
`https://stats.antonlozhkin.ru/pt/ping?os=mac|win&v=<версия>[&id=<32 hex>&on=0|1]` и получает
`{"latest": "<номер последнего выпуска>", "url": …}`. Номер новее своего — в панели строка «Доступна версия…»
со ссылкой на файл выпуска (`releases/latest/download/…`). Сама программа не скачивает и не ставит обновления.

- `id` — случайный номер установки (UUID без дефисов), в `stats.json` в папке программы; `id` и `on` уходят только
  при включённой галочке «Отправлять анонимную статистику» (Mac — `UserDefaults` `sendStats`, Windows —
  `HKCU\Software\Proxy Tunnel\SendStats`). Без них запрос только узнаёт версию.
- Сервер не хранит IP (nginx `access_log off`, отказы по частоте ниже уровня журнала), хранит по номеру: день
  первого запроса, систему, версию и дни запросов за последние 35 дней. Номер последней версии сервер берёт у
  GitHub (`releases/latest`, раз в час). Код сервера — не в этом репозитории.
- Файлы: `menubar/Update.swift`, `windows/Update.cs`.

Выпуск новой версии: поднять номер в `menubar/build.sh` (`CFBundleShortVersionString`) и
`windows/ProxyTunnel.csproj` (`Version`), собрать `menubar/package.sh`, взять `ProxyTunnel-windows.exe` из
сборки GitHub Actions и опубликовать выпуск с тегом `vX.Y` и обоими файлами под теми же именами — ссылки
`releases/latest/download/…` в README и в программе начнут вести на него, а программы увидят его в течение часа.

## Ключи

Ключи программы — в её папке, не в `~/.ssh`; ключи пользователя только пробуются при входе. Годный ключ
используется повторно (недостающий `.pub` восстанавливается), негодный — не ключ, ключ с паролем, `.pub` без
закрытого — откладывается как `<имя>.old-<время>`, не удаляясь. В комментарии ключа — имя компьютера
(`proxy-tunnel@…`). На сервере повтор того же ключа не дублируется (`sort -u`, `grep -qxF`).

| | macOS | Windows |
|---|---|---|
| папка | `~/Library/Application Support/Proxy Tunnel/` | `%APPDATA%\Proxy Tunnel\` |
| ключ туннеля / входа | `id_ed25519` / `admin_ed25519` | `tunnel_rsa` / `admin_rsa` (RSA 3072: ed25519 средствами .NET не создать) |
| ключ сервера | `known_hosts` | `known_hosts.json` (SHA256 по `адрес:порт`) |
| журнал | `~/Library/Logs/Proxy Tunnel.log` | `%APPDATA%\Proxy Tunnel\log.txt` |

## macOS (`menubar/`)

- Значок и панель — свои `NSStatusItem` и `NSPopover` (`AppDelegate` во `Views.swift`), а не `MenuBarExtra`:
  панель `MenuBarExtra` нельзя открыть из кода.
- ssh — системный `/usr/bin/ssh`; пароль — через временный `SSH_ASKPASS` (OpenSSH ≥ 8.4, в macOS 13 — 9.0).
- **Рядом с VPN-клиентом.** Подключённый VPN становится основной сетевой службой, и macOS берёт настройки прокси
  у неё, а не у Wi-Fi — поэтому PAC ставится на все включённые службы, VPN-службы тоже (проверено с Happ в режиме
  TUN). Служба с чужим включённым PAC не трогается; прежнее состояние — `pac-services.json`, возвращается при
  выключении. ssh туннеля привязан к интерфейсу прямого выхода (`BindInterface`, `Net.physicalInterface`);
  сервер, заданный именем, ищется через DNS-over-HTTPS по этому интерфейсу (`Net.prepare`). Не работает рядом
  с клиентом, у которого жёсткий «kill switch».
- Файлы: `Config.swift` (настройки, PAC), `Net.swift` (интерфейс, DNS), `Tunnel.swift` (ssh, PAC-сервер),
  `Setup.swift` (ssh от имени админа), `Model.swift` (состояние, проверки, настройка), `Views.swift` (окна),
  `Update.swift` (новая версия, статистика). Новый файл — дописать в список `swiftc` в `build.sh`.
- Сборка: `menubar/build.sh` (swiftc, Intel + Apple Silicon, подпись ad hoc; Command Line Tools, macOS 13+);
  `menubar/package.sh` → `dist/ProxyTunnel-mac.dmg`. Тестов нет: проверка — сборка и `bash -n` скриптов.
- Скрипты: `check.sh` (те же проверки, последняя строка «МОЖНО»/«НЕЛЬЗЯ»), `mode.sh on|off` (прокси и PAC без
  программы).
- Не нотаризовано: первый запуск — правый щелчок → «Открыть» (macOS 15+: «Конфиденциальность и безопасность» →
  «Всё равно открыть»).

## Windows (`windows/`)

- C# / .NET 8, WinForms: значок у часов (`NotifyIcon`), панель над ним, окно настроек — `UI.cs`; логика —
  `Core.cs`; ssh, ключи, туннель, PAC, системный прокси, настройки Claude Code — `Infra.cs`.
- ssh — библиотека SSH.NET (туннель — `ForwardedPortLocal`), без системного `ssh.exe`: на Windows 10 он старый
  и не умеет передавать пароль из программы.
- PAC — значение `AutoConfigURL` в `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` (права
  администратора не нужны) с уведомлением системы через `InternetSetOption`. К адресу добавляется `?v=<время>`,
  чтобы Windows не брала старый PAC из кэша после смены списка. Чужой `AutoConfigURL` не трогается; при
  выключении наш удаляется. Обычный прокси (`ProxyEnable`) от другой программы — проверка о нём говорит.
- Автозапуск — `HKCU\…\Run`. Одна копия программы — именованный мьютекс.
- Сборка — GitHub Actions (`.github/workflows/windows.yml`, `windows-latest`):
  `dotnet publish -r win-x64 --self-contained -p:PublishSingleFile=true` → артефакт `ProxyTunnel-windows.exe`.
  Локально на Маке не собирается (нет .NET SDK). Подписи нет: SmartScreen предупредит при первом запуске.
- Привязки ssh к интерфейсу и DNS мимо VPN-клиента в Windows-версии нет.
